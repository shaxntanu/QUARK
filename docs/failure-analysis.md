# Failure analysis

This lightweight analysis covers the main failure modes of the local Windows companion, USB protocol, and ESP32-C3 display. It is not a formal safety analysis.

| Failure mode | Likely cause | Effect | Detection | Mitigation | Recovery | Residual risk |
|---|---|---|---|---|---|---|
| USB device disconnects or serial port is busy | Unplug, cable fault, another program owns the port | Device stops receiving current telemetry; display may age out | Companion logs serial errors; firmware freshness timeout changes selected-feed status | Port discovery, bounded handshake, reconnect loop, per-feed freshness timers | Reconnect the device and close other serial tools | Cable, USB power, and physical connector faults are not tested here |
| Malformed or oversized serial line | Noise, incompatible firmware, or another local process writes to the port | A line is discarded; accepted display data may become stale | Strict ASCII decode, exact command whitelist, and firmware line-overflow handling | Count CR bytes against the line bound; discard invalid data through LF; never ignore malformed bytes during decoding | Send a valid refresh after the link is healthy | USB serial has no authentication, so another local process can inject data |
| Codex App Server is unavailable | CLI missing, sign-in expired, server exit, or network interruption | Codex pages show offline or stale readings; PC sampling continues | App Server child-process and request errors; freshness timeout | Separate Codex worker, bounded retries, selected-feed grace period, stale-data expiry | Restore CLI sign-in or network access; switch to system mode while Codex recovers | No live outage/recovery test was performed |
| System or Codex reading is stale | A collector stalls or a source stops replying | The OLED may briefly retain an old value | Mode-specific age limits | Expire stale readings and show offline status | Resume collection or change mode | Physical transition timing is untested |
| MCU reset or unstable power | USB interruption, clone regulator issue, or brownout | OLED and controls restart; host may need to rediscover the device | Startup banner and serial handshake | Host-side discovery; local switch/button state is initialized at boot | Restore stable USB power and allow the handshake to complete | Reset-cause logging and brownout margins are not measured |
| OLED or I2C connection fails | Loose wiring, wrong pin order, incompatible display, or bus fault | Screen is blank or corrupted while the companion may continue | Visual inspection; firmware does not report a verified display-ready status to the host | Document J1 pin order and the SH1106 128x64 constructor | Check power, SDA/SCL wiring, module controller, and I2C connection | No automatic recovery or physical display test was recorded |
| SuperMini clone does not match the PCB | Different row spacing, pinout, USB connector placement, or module outline | Module may not fit or a signal may be miswired | Compare the actual module with the KiCad footprint before assembly | Mark exact MPN unknown; verify dimensions and pinout before ordering | Do not force the module into the sockets; select a compatible module or revise the carrier | Clone variation is not captured by one generic footprint |
| Untrusted local process writes serial commands | Any process with access to the COM port | Spoofed readings or mode/refresh commands | No cryptographic identity exists on the link | Treat the Windows account and attached USB device as trusted; whitelist commands and bound payloads | Close the conflicting process and restart the companion | Local USB access is not an authorization boundary |

The tests cover parser and packet boundaries, not physical failure injection. Hardware recovery claims remain unverified until a device-level acceptance run is recorded.
